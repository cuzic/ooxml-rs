# ADR-0002: Schema-driven code generation for the typed lens

- Status: **Proposed** (draft, not yet reviewed)
- Date: 2026-11-16
- Depends on: [ADR-0001](0001-lossless-round-trip-architecture.md)

## Context

ADR-0001's Layer 2 puts a *typed lens* over a lossless `RawNode` tree.
To do that for any element, the lens needs per-element schema knowledge
that the raw tree does not carry:

- the element's qualified name, and which complex type it has *in this
  parent* (the same local name maps to different types in different
  contexts — e.g. `x:dimension` is `CT_SheetDimension` under
  `<worksheet>` but `CT_PivotDimension` elsewhere; `x:row` and
  `x:sheetData` likewise have external-link variants);
- its attributes: names, simple types, defaults, enumerated values;
- its content model (the XSD *particle*): which children are allowed,
  their cardinality, and — critically for writes — their **order**. A
  child inserted out of schema order is the classic way to make Excel
  show a repair dialog, and ADR-0001's T2 locality oracle already
  requires "the insertion point respects ordering".

The volume makes hand-writing this a non-starter. Counting element
declarations in the Open XML SDK schema data (see Sources): SpreadsheetML
has 445 in the base namespace plus 474 across 45 Microsoft extension
namespaces; WordprocessingML 685 + 166; PresentationML 248 + 178; shared
DrawingML/charts/diagrams add roughly 1,300 more. Across all schema
files, 2,122 complex types carry a content model.

Phase0 (ADR-0001's scope) needs only a handful of these — `worksheet`,
`sheetData`, `row`, `c`, `f`, `v`, `is`, `t`, `dimension` — but this
decision has to be made now so Phase0's hand-written lens code is the
first instance of the generated shape, not a one-off that gets thrown
away later.

The research that led here (conversation of 2026-11-16) also examined
`ooxmlsdk` in depth, since it already generates Rust from the same data;
its findings are recorded under Alternatives.

## Decision

### 1. Input: Open XML SDK's metadata, vendored and pinned

The generator reads the .NET Open XML SDK's machine-readable schema
metadata (`data/schemas/*.json`, `data/parts/*.json`,
`data/namespaces.json`), not the ECMA-376 XSDs directly. These files
already resolve XSD groups, extensions, and substitutions into one
particle tree per type, and they cover the Office 2010–Microsoft 365
extension namespaces that ECMA-376 does not.

- The files are **vendored** under `reference/openxml-sdk-data/`, pinned
  to a specific upstream commit (the one examined for this ADR is
  `dotnet/Open-XML-SDK@431ab05c`, 2026-08-18), together with upstream's
  `LICENSE` (MIT, .NET Foundation) and a `PROVENANCE.md` recording the
  commit and a checksum. About 10 MB uncompressed; only these three
  inputs, not the rest of the SDK.
- Updating the data is an explicit, reviewed commit (bump pin →
  regenerate → review the generated diff), never a build-time fetch.
- Local corrections, when the SDK data disagrees with real Office
  output, go in a separate checked-in overrides file applied by the
  generator — not by editing the vendored files. (`ooxmlsdk` maintains
  exactly such an overrides layer, `sdk_data/schema_extensions/`, which
  is evidence the need is real.)

### 2. Generator: an offline `xtask`, output checked in

- A workspace member `xtask` (`publish = false`) provides
  `cargo xtask codegen`. It writes ordinary Rust source to
  `crates/ooxml-<format>/src/generated/<namespace>.rs`, each file headed
  `// @generated by cargo xtask codegen — do not edit`.
- Generated files are committed. They are greppable, reviewable,
  rustdoc- and IDE-visible, and add zero cost to a downstream build.
- `cargo xtask codegen --check` regenerates into memory and fails on any
  diff; CI runs it. Hand-edits to generated files are therefore caught
  rather than silently overwritten.
- **Not used:** `build.rs` generation (cost on every downstream build,
  generated code invisible to review) and procedural macros for the
  schema surface (compile-time cost at thousands of types, poor
  rust-analyzer visibility). `macro_rules!` may be emitted inside
  generated files for repetitive accessor bodies.

### 3. Shape of generated code: constant tables + thin accessors

The split is: **all behavior is hand-written once in `ooxml-core`;
generated code is data plus one-line wrappers.**

Hand-written (`ooxml-core`):

```rust
pub trait ElementSpec: 'static {
    const QNAME: QName;
    const ATTRS: &'static [AttrSpec];   // name, simple type, default
    const CONTENT: Content;              // see §4
}

#[diagnostic::on_unimplemented(
    message = "`{Self}` is not an allowed child of `{P}`",
    note = "allowed children are listed in `{P}::CONTENT`")]
pub trait ChildOf<P: ElementSpec>: ElementSpec {}

impl<'a, E: ElementSpec> Lens<'a, E> { /* typed reads over RawNode */ }
impl<'a, E: ElementSpec> LensMut<'a, E> {
    pub fn insert<C: ChildOf<E>>(&mut self) -> Result<LensMut<'_, C>, Error>;
}
```

Generated (per complex type actually in the allowlist, §5):

```rust
/// `x:c` (CT_Cell) — Cell.
pub enum Cell {}                                   // uninhabited marker
impl ElementSpec for Cell {
    const QNAME: QName = qn!(SML, "c");
    const ATTRS: &'static [AttrSpec] = &[
        attr!("r", Str), attr!("s", U32, default = "0"),
        attr!("t", Enum(&CELL_VALUES), default = "n"), /* … */
    ];
    const CONTENT: Content = Content::Sequence(&[
        item!(SML, "f", 0..=1), item!(SML, "v", 0..=1),
        item!(SML, "is", 0..=1), item!(SML, "extLst", 0..=1),
    ]);
}
impl ChildOf<Row> for Cell {}
impl<'a> Lens<'a, Cell> {
    pub fn style_index(&self) -> Result<u32, AttrError> { self.attr_or_default("s") }
}
```

Notes on this shape:

- Content-model items refer to children **by QName**, not by Rust type.
  A child that isn't in the generation allowlist still has its correct
  position in its parent's `CONTENT`, so ordering is right even for
  elements ooxml-rs has no typed API for yet.
- Markers are keyed by *complex type in context* (`CT_SheetDimension`
  vs `CT_PivotDimension`), not by local name, matching how the SDK
  data itself is keyed (`"x:CT_Cell/x:c"`).
- Rust names come from the SDK's `ClassName`/`PropertyName`
  (snake-cased for methods), keeping names traceable to the .NET SDK's
  documentation; the schema QName is always in the doc comment.
- **Enumerated attribute values must not be lossy.** A typed read of an
  enum attribute returns the known variant or an `Unknown(&str)` value,
  never an error that tempts callers into rewriting it, and an untouched
  attribute is never re-rendered (ADR-0001 Layer 2 already guarantees
  the latter). Files written by newer Office versions carry values the
  pinned data may not know.
- Generated tables are additionally checked at compile time with inline
  `const { … }` assertions (no duplicate QNames within a sequence, every
  default parses as its simple type), so a generator bug fails the build
  of this crate rather than reaching users. The generator performs the
  same checks first, with better error messages.

### 4. Content models: flat sequences now, general particles later

The SDK data's particle kinds across all schemas: 11,278 `Element`,
2,234 `Sequence`, 1,227 `Choice`, 1,150 `Group`, 142 `Any`, 6 `All`.
**754 of the 2,122 types with a content model are not a flat sequence
of elements** (nested choices, repeated groups, `Any` wildcards) — e.g.
most of WordprocessingML's paragraph/run content.

`Content` is therefore an enum, and this ADR only commits to
implementing one case:

- `Content::Sequence(&[Item])` — a flat sequence of elements, each with
  its own cardinality. **Insertion rule:** the new child goes
  immediately before the first existing sibling whose schema position
  is greater than the new child's; if there is none, after the last
  existing sibling. Siblings the schema does not list (vendor
  extensions, `mc:AlternateContent`, comments, processing instructions)
  are not used to decide the position, and inserting a child never
  moves them relative to one another. (Their position relative to the
  new child is defined by the known siblings around them; T2 checks the
  result.)
- `Content::Particle(&ParticleTree)` — generated for every other type
  so the data exists, but `insert` on such a parent returns
  `Err(Error::UnsupportedContentModel)` until a later ADR specifies
  matching and insertion for choices and repeated groups. Typed *reads*
  of such elements work regardless; only insertion is gated.
- `Content::Empty` / `Content::Text(SimpleType)` for leaf elements.

All Phase0 types are flat sequences or leaves (verified against the
data): `worksheet` (38 elements in order), `sheetData` (`row*`), `row`
(`c*`, `extLst?`), `c` (`f?`, `v?`, `is?`, `extLst?`), `is`
(`t?`, `r*`, `rPh*`, `phoneticPr?`); `f`, `v`, `t`, `dimension` are leaves.

### 5. Scope control: allowlist + per-namespace features

- The generator takes an explicit allowlist of complex types per
  format. Phase0's allowlist is exactly the types in §4's last
  paragraph. Growing ooxml-rs's typed surface means growing the
  allowlist, i.e. a reviewable generated diff.
- Each namespace group is behind a cargo feature (`sml`, `wml`, `pml`,
  `dml`, plus per-extension features later), switched in generated code
  with `cfg_select!` (Rust 1.95, within the 1.99 MSRV). Phase0 ships
  only `sml`, on by default in `ooxml-xlsx`.
- The SDK's `InitialVersion` (Office 2007/2010/…) is carried into the
  tables as data but has no behavioral effect in Phase0.
- Markup Compatibility (`mc:AlternateContent`, `mc:Ignorable`) is out of
  scope: the lens treats those elements as unlisted siblings (§4),
  i.e. preserved and never navigated into.

### 6. Package parts

`data/parts/*.json` (128 part kinds: content type, relationship type,
allowed child parts) is generated into a similar constant table for
`ooxml-core::Package`'s Layer 3 registries. Phase0 only reads it
(identifying a worksheet part by relationship type); adding parts
remains out of scope per ADR-0001.

## Alternatives considered

1. **Depend on `ooxmlsdk` (v0.15.0) as the typed layer.** It generates
   Rust from the same SDK data, models every part, reuses original
   compressed bytes for unloaded parts (matching ADR-0001 Layer 1), and
   reports 5,477/5,477 files passing round-trip across five corpora.
   Rejected as the Layer 2 foundation, from reading its source:
   - Children that match no generated type are dropped on read — its
     derive emits `skip_element` for unmatched children
     (`ooxmlsdk-derive/src/sdk_type.rs`, `build_unmatched_child_tokens`);
     its README lists unknown-element DOM editing as not yet exposed.
     ADR-0001 requires such siblings (e.g. the fixture's foreign
     `<extLst>`) to survive.
   - A loaded part is fully re-serialized from typed structs, in schema
     order with canonical lexemes. Its round-trip suite opens every part
     eagerly and compares after XML canonicalization with 47
     normalization functions (child reordering, duplicate removal,
     numeric lexemes) in `ooxmlsdk-test-suite`'s
     `crates/ooxmlsdk-corpus-test-support/src/roundtrip.rs`. That is a
     strong semantic-equivalence result, but a different guarantee from
     ADR-0001's byte-exact untouched siblings.
   It remains valuable as a **reference and test oracle** (e.g. a
   dev-dependency that cross-checks that ooxml-rs output parses), and
   its overrides layer is worth consulting when the SDK data is wrong.
2. **`ooxmlsdk`-style typed structs + derive macro, self-built.** Same
   data, our own code. Rejected for the same structural reason as (1):
   typed structs as the storage model are ADR-0001's alternative 1b,
   already set aside for Phase0. Generating *tables over a raw tree*
   keeps storage lossless and makes typing a view.
3. **Read ECMA-376 XSDs directly.** Authoritative for the standard
   namespaces, but requires a real XSD processor (groups, extensions,
   substitution groups, redefinitions) and does not cover the Microsoft
   extension namespaces that real files are full of. Not chosen;
   revisit only if the SDK data proves unreliable in ways an overrides
   file cannot fix.
4. **`build.rs` generation.** Rejected (§2): per-build cost for every
   downstream user, generated code invisible to review.
5. **Procedural macros over hand-written declarations.** Still needs
   the data from somewhere; at this scale it moves cost to every
   compile and hides the result from rust-analyzer. Reconsider for
   small, hand-written API surfaces once `macro_rules!` derive macros
   (RFC 3698, `macro_derive`) are stable — not stable as of Rust 1.99.
6. **serde-based XML mapping or XSD→serde generators.** Rejected: the
   serde data model loses sibling order and unknown content by
   construction, which is the failure mode ADR-0001 exists to avoid.

## Consequences

- Positive: Phase0's hand-written lens for `c`/`row`/`sheetData` is the
  first consumer of the generated shape, so nothing written now is
  throwaway; broadening coverage is "extend the allowlist, review the
  diff".
- Positive: schema violations in *insertion* become compile errors with
  readable messages (`ChildOf` + `#[diagnostic::on_unimplemented]`),
  not Excel repair dialogs found later by hand.
- Positive: the generated output is mostly constant data, expected to
  be much smaller than `ooxmlsdk`'s ~136k generated lines. Not
  measured; to be recorded once the generator exists.
- Negative: 754 content models (and most of WordprocessingML's
  interesting ones) get read-only typed access until a follow-up ADR
  defines general particle insertion. This is the main open design
  problem this ADR defers, deliberately.
- Negative: ooxml-rs inherits the SDK data's interpretation of the
  schemas, including its mistakes; the overrides file is the escape
  hatch, and every override needs a recorded reason (and ideally a
  real-Office-authored fixture).
- Negative: about 10 MB of vendored third-party data enters the
  repository, with MIT attribution obligations to keep.

## Open questions (for review)

1. Vendor the whole `data/schemas` directory, or only the namespaces
   in the current allowlist (smaller repo, but every allowlist growth
   may need a data refresh)?
2. Should marker types be uninhabited enums (as sketched) or unit
   structs? It only matters if a value of the type is ever needed.
3. Should the `Unknown(&str)` enum variant be a separate wrapper type,
   so that ordinary `match` on a known-values enum stays exhaustive?
